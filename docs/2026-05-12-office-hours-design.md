# AI 健身管家 — Office Hours 设计文档

**日期：** 2026-05-12
**阶段：** Pre-product（产品前，无真实用户）
**模式：** 创业 / YC 产品诊断

---

## 项目现状

用户每次运动前填问卷（精力/状态/时间/地点）→ AI 决策强度和风格 → 匹配动作库 → 输出训练计划 → 收集反馈 → 更新用户记忆。

已有：`user_profile_schema.json`、`matching_logic.json`、`exercise_library.json`、LoRA 微调脚本（Qwen3-8B）、约 400 条 SFT 训练数据、SparkyFitness Docker 部署。

---

## 诊断发现

### Q1 — 需求真实性
**证据：市场调研推断，无真实用户验证。**

没有任何一个具体的人曾经因为缺少这个产品而遭遇可量化的损失。行业报告（《线上健身指导行业深度研究报告》）证明市场存在，但不证明用户需要这个产品形态。

### Q2 — 现状替代方案
用户目前花钱请教练或购买课程。这证明需求的底层驱动力是真实的，但竞争对手不是"没有方案"，而是"有人工服务替代"。

### Q3 — 目标用户
群体划分存在（有一个用户分类框架），但无法命名具体一个人、他的日常运动场景、和因为没有这个产品而导致的具体后果。

### 核心风险模式
**"假设驱动"而非"需求驱动"的产品开发。**

## 未验证前提（必须先验证再深入）

| 前提 | 风险 | 验证方式 |
|------|------|---------|
| 用户愿意每次运动前填问卷 | 高——如果不愿意，整个个性化机制失效 | 观察5个真实用户的实际行为 |
| 用户信任 AI 方案胜过自己习惯 | 中——健身用户有强固定习惯 | 看他们实际遵照率 |
| "按状态调整"的痛苦值得装专门 App | 中——可能只是一个功能，不是一个产品 | 和现有 App 集成是否足够 |

## MVP 方案对比

### 方案 A：最小化问卷 + Claude API（2-3天）
只问3个问题 → Claude API 直接生成方案 → 发给用户。不需要微调模型，不需要复杂数据结构。目标：验证用户会不会用。

### 方案 B：人工教练代理（今天起，零工程）
找5个真实用户，他们运动前发消息，人工用 matching_logic 给方案。目标：验证需求形态和用户行为。

### 方案 C：完整系统（3-6个月）
原计划：Qwen3-8B LoRA + 完整匹配逻辑 + 用户记忆。在需求验证前投入。


## 本次 Office Hours 作业

找 5 个平时在健身的人（不需要是陌生人），让他们在运动前发消息告诉你：
1. 今天精力怎么样（1-5分）
2. 有多少时间
3. 在哪里练

你根据 `matching_logic.json` 手动给他们一个方案。

连续做2周。观察：
- 他们有没有每次真的发消息（意愿测试）
- 他们有没有按方案练（信任测试）
- 他们事后有没有反馈"这个很好用"（价值测试）

**如果2周内没有一个人每天都发消息，说明"每次运动前报告状态"这个行为不成立，需要重新设计交互入口。**
